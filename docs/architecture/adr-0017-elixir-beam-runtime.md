# ADR 0017 — Elixir/BEAM runtime sidecar

Status: proposed for issue #943. This ADR governs `runtime.elixir` and the
`sdks/elixir` Mix project.

## Decision

Blok exposes Elixir nodes through a long-lived, OTP-supervised gRPC sidecar.
The runner remains the workflow engine and policy boundary; the sidecar owns
node code, typed JSON contracts, process isolation, and runtime-local
observability.

The public API is a behavior/macro-based module:

```elixir
use Blok.Node, name: "fetch-user", input: Input, output: Output
def execute(ctx, %Input{} = input), do: {:ok, %Output{...}}
```

Input/output modules use `Blok.Schema`. Field names are compile-time atoms,
while JSON keys and metadata remain binaries. Unknown wire keys are rejected,
stable issues use JSONPath-like paths (`$.user_id`), and schemas reflect to
canonical JSON Schema. `Jason` is the JSON codec; `ex_json_schema` is retained
for semantic fixture validation rather than exposing schema internals to node
authors.

Node discovery is compile-time registration through `config :blok, nodes:`.
The CLI copies project node modules into the Mix `lib` path and generates a
config registry; the sidecar never scans arbitrary files or converts node names
into atoms at boot.

## Supervision and admission

The application tree contains a bounded `Task.Supervisor`, `Blok.Registry`,
`Blok.Admission`, and `GRPC.Server.Supervisor`. Admission limits active jobs and
the pending queue (`BLOK_ELIXIR_MAX_CONCURRENCY` and
`BLOK_ELIXIR_MAX_QUEUE`). Saturation returns the deterministic
`RUNTIME_OVERLOADED` structured error. A node exception or task crash is turned
into one failed execution; the endpoint and unrelated jobs stay supervised.

Each execution receives an atomic cancellation token and monotonic deadline.
Nodes should call `Blok.Context.check_cancelled!/1` around cooperative I/O or
loops. The admission owner kills a timed-out monitored task, and drain stops
new admission before bounded shutdown. User nodes must use the context's task
facilities or their own supervision; unlinked arbitrary processes are not part
of the supported descendant-cancellation guarantee.

## Wire, security, and observability

The canonical source is `proto/blok/runtime/v1/runtime.proto`; Elixir bindings
are generated by `mix proto.generate` and checked in as generated output.
`ListNodes` advertises schemas, capability manifests, and `blob-v1` only when a
bounded readable `BLOK_BLOB_DIR` is configured. Claim-check ids are restricted
to two safe path segments and reads are capped by `BLOK_BLOB_MAX_BYTES`.

All configuration is read from the environment by `Blok.Config` and validated
at startup: a malformed value fails the boot naming the variable instead of
silently reverting to a default. `BLOK_LOG_LEVEL` is resolved through a fixed
allow-list rather than `String.to_atom/1`.

The sidecar accepts the shared `BLOK_GRPC_MAX_MESSAGE_BYTES` ceiling, honours
`BLOK_GRPC_KEEPALIVE_TIME_MS`/`BLOK_GRPC_KEEPALIVE_TIMEOUT_MS` as Cowboy
idle/inactivity/settings ceilings (the BEAM server sends no HTTP/2 keepalive
pings), supports
TLS with `BLOK_GRPC_TLS_CERT`/`BLOK_GRPC_TLS_KEY` (and optional CA for mTLS), and emits
structured `NodeError` values with runtime/node identity. `Blok.Logger` bounds
large values and redacts likely secrets, and `Blok.Logger.safe_inspect/1`
bounds crash reasons before they become error envelopes. Execution telemetry is
published on `[:blok, :execution, :start | :stop | :exception]` with
`duration_ms`/`queue_time_ms` measurements and identity-only metadata
(`node`, `run_id`, `workflow`). Capability manifests contain opaque
reference names only; policy evaluation remains in the TypeScript runner.

## Compatibility and limitations

The supported baseline is Elixir `~> 1.17`, OTP `27+`, and the `grpc`/
`grpc_server` `1.0.x` line. Mix release and non-root container assets are
included by the SDK scaffold; the first slice does not require Phoenix, does
not promise distributed Erlang clustering, hot code upgrades, or arbitrary NIF
scheduling. CPU-heavy work must be moved to an explicit dirty-NIF/worker policy
chosen by the application; the SDK cannot make an unknown NIF safe.

## Conformance evidence

- `sdks/elixir/test/schema_test.exs` — typed schemas, stable validation paths, and atom safety.
- `sdks/elixir/test/node_test.exs` — typed node execution, output validation, reflection, and capability metadata.
- `sdks/elixir/test/admission_test.exs` — bounded admission and recovery.
- `sdks/elixir/test/beam_failure_modes_test.exs` — concurrent isolation, bounded
  processes/queue/mailbox, deterministic `RUNTIME_OVERLOADED`, raise/throw/exit/
  crash mapping, descendant cleanup, deadline propagation, supervisor recovery,
  graceful drain, atom-table safety, and secret redaction.
- `sdks/elixir/test/config_test.exs` — env-configured and startup-validated port,
  message size, keepalive, connections, TLS/mTLS, concurrency, queue, and log level.
- `sdks/elixir/test/telemetry_test.exs` — execution start/stop/exception events
  with duration and queue time, and identity-only metadata.
- `sdks/elixir/lib/mix/tasks/blok.bench.ex` — repeatable gRPC load profile; the
  recorded run is in `docs/architecture/runtime/elixir-conformance.md`.
- `scripts/sync-proto.ts --check` — generated proto source parity.
- `core/runner/src/RuntimeRegistry.ts` and `core/runner/src/Configuration.ts` — canonical adapter registration and port/env wiring.

The full cross-runtime gRPC chain and real scaffold/boot smoke lane remain
CI-dependent on an installed Elixir toolchain; unsupported hosts must report a
clear skip rather than silently claiming Elixir conformance.
