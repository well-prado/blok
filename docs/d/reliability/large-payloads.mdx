Blok runs non-NodeJS nodes (`runtime.python3`, `runtime.rust`,
`runtime.go`, …) as **gRPC sidecar processes**. When a workflow calls one,
the runner serializes the step's data and sends it over gRPC. That data is
**fully buffered in memory on both ends** of a single unary message — there
is no streaming — so a hard message-size limit protects both processes from
unbounded memory use.

<Note>
This applies **only** to nodes that run in another runtime. In-process
NodeJS/TypeScript nodes pass data by reference with no boundary and no limit.
</Note>

## The limit

| Setting | Default | Ceiling |
|---|---|---|
| `BLOK_GRPC_MAX_MESSAGE_BYTES` | 16 MiB | 256 MiB |

The limit is **symmetric** and **not negotiated over the wire** — the runner
and every sidecar read the same env var independently. If you raise it, you
must set the **same value on both the runner and the sidecar**, or the
under-configured side rejects oversized messages with a gRPC
`RESOURCE_EXHAUSTED`.

## What counts toward the limit

Each remote node call inlines two things into one message:

- **inputs** — the step's mapped inputs.
- **trigger body** — the original request/job payload.

<Note>
**Accumulated state** (`ctx.state`, every prior step's output) and the
**previous step's output** are **not** sent, since v2.2. They used to be, and
because state grows as a workflow progresses, a `runtime.*` node inside a
`forEach` re-shipped a payload that grew with the loop — per-call cost linear
in the run's state, total cost quadratic in the number of items.

Set `BLOK_GRPC_STATE_DIET=0` to restore the old payload if one of your nodes
reads `ctx.vars` / `ctx.response.data` inside its own body. That is a
process-wide switch; the per-node fix is to map the value the node needs into
that step's `inputs`. State still flows **back** from the node via
`vars_delta` either way.
</Note>

## The fail-fast error

When the encoded request would exceed the limit, the runner fails the step
**before dispatch** with a `GRPC_REQUEST_TOO_LARGE` error naming the node and
a per-blob byte breakdown — instead of the opaque `RESOURCE_EXHAUSTED` the
sidecar would otherwise raise mid-flight. Read the breakdown to see which
blob is the offender.

This guard runs **after** the claim-check offload below, so it only fires on
data that really is crossing the wire inline.

## Automatic claim-check (`BLOK_BLOB_DIR`)

Rather than restructure a pipeline around the limit, you can let the runner do
the claim-check for you. Point `BLOK_BLOB_DIR` at a directory the runner **and
the sidecar both see** and oversized step inputs stop travelling inline:

- Inputs larger than `BLOK_BLOB_THRESHOLD_BYTES` (default 1 MiB) are written to
  that directory, and the message carries a small reference instead —
  `{"$blokBlob": {"id": …, "bytes": …, "codec": "json"}}`.
- The sidecar reads the file and hands the node its **real** inputs. Node code
  is unchanged; it never sees a reference.
- The blob is deleted as soon as the call finishes, so disk use tracks
  concurrent oversized calls, not run history. The janitor sweeps anything a
  crashed runner left behind after `BLOK_BLOB_RETENTION_MS` (default 1 h).

<Note>
The runner sends a reference **only** to a runtime that advertises the
`blob-v1` capability on `ListNodes`, which an SDK does exactly when its own
`BLOK_BLOB_DIR` is set. A runtime that doesn't advertise it keeps receiving
inline data and the fail-fast error above — so a half-configured deployment
degrades loudly instead of handing a node a reference it can't read.
</Note>

| Setting | Default | Meaning |
|---|---|---|
| `BLOK_BLOB_DIR` | *(unset — feature off)* | Shared directory. Set it on the runner **and** every sidecar. |
| `BLOK_BLOB_THRESHOLD_BYTES` | 1 MiB | Inputs above this are offloaded. |
| `BLOK_BLOB_RETENTION_MS` | 1 hour | How long the janitor keeps orphaned blobs. |

**Where the directory comes from.** Same host in dev (`bun scripts/dev-full.ts`
sets `.blok/blobs` for every process it spawns). In Kubernetes, set
`blobStore.enabled=true` in the Helm chart — it mounts one shared `emptyDir`
into the runner and every runtime sidecar in the pod and sets `BLOK_BLOB_DIR`
on all of them. A runtime on a **different host** has no shared filesystem, so
it simply won't advertise the capability; use the manual mitigations below.

<Warning>
All seven SDKs resolve `$blokBlob` references. Only the **request** direction
is offloaded — a node's *return value* still travels inline and is still
bounded by the message limit.
</Warning>

## Staying under the limit

1. **Don't inline bulk data.** Pass a **reference** (an id, an object-store
   key, a file path both sides can reach) and have the node fetch the bytes
   itself — the claim-check pattern. `BLOK_BLOB_DIR` above automates this for
   step inputs; do it by hand when your runtime can't use it.
2. **Keep bulk values out of the step's inputs.** Map only what the node
   reads. Accumulated state no longer rides along (see the note above), so
   what you map is what you pay for.
3. **Split the pipeline** so no single boundary crossing carries everything.
4. **Raise the limit** as a last resort: set `BLOK_GRPC_MAX_MESSAGE_BYTES` (up
   to 256 MiB) on **both** the runner and the sidecar, accepting that peak
   memory ≈ `forEach`-concurrency × message size on each side.
