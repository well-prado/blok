<Warning>
  **This is the runtime wire format emitted by the lowering pass. It is not an
  authoring API. You never write these strings by hand.**

  You author with **typed handles** — `step()` returns a handle you pass into
  later steps ([handles and footguns](/d/primitives/handles-and-footguns)) — or,
  in JSON, with **structural references** (`{"$ref": {"step", "path"}}`). A
  deterministic pass at the workflow load boundary compiles those into the
  strings on this page, which is the only form the engine has ever resolved.

  Read this page when you are **debugging a lowered workflow** — a stack trace,
  a `MapperResolutionError`, a `.blok/` build artifact, or a Studio trace that
  shows the resolved wire string. To write a workflow, start at
  [workflows](/d/introduction/workflows) or the
  [JSON workflow reference](/d/cli/workflows).
</Warning>

## Where these strings come from

Blok's IR carries structural handle references. `lowerRefs`
([`core/shared/src/utils/lowerRefs.ts`](https://github.com/deskree-inc/blok/blob/main/core/shared/src/utils/lowerRefs.ts))
runs once at the workflow **load boundary**, before the mapper, and compiles
every structural reference into exactly the string form documented below. The
mapper engine itself is untouched by the typed-handle redesign — that is the
point of the design (ADR 0001): the authoring surface changed, the runtime did
not.

| You author | Lowering emits |
|---|---|
| `step("fetch", …)` → handle `fetched` | `js/ctx.state.fetch` |
| `fetched.data.items` | `js/ctx.state.fetch.data.items` |
| the trigger entry handle, `req.body.url` | `js/ctx.request.body.url` |
| the `error` handle in a `tryCatch` catch arm | `js/ctx.error` |
| `` tpl`chat:${sessionId}` `` | ``js/`chat:${ctx.request.params.sessionId}` `` |
| JSON `{"$ref": {"step": "fetch", "path": ["data"]}}` | `js/ctx.state.fetch.data` |
| JSON `{"$tpl": ["chat:", {"$ref": …}]}` | ``js/`chat:${…}` `` |

Step ids that are not valid JS identifiers are lowered with bracket notation
(`js/ctx.state["fan-out"]`), and numeric path segments become `[0]`.

## `js/` prefix (full expression)

```json
"inputs": { "url": "js/ctx.request.body.url", "headers": "js/ctx.request.headers" }
```

The whole field is replaced by evaluating the JS expression (after stripping
the `js/` prefix) against the live `ctx`.

## What's in scope

| Identifier | Value |
|---|---|
| `ctx` | The full Context — `ctx.request`, `ctx.state`, `ctx.vars`, `ctx.logger`, `ctx.error`. |
| `data` | `ctx.response?.data` (last step's data) or `ctx.request?.body` as fallback. |
| `vars` | `ctx.vars` — alias of `ctx.state` for back-compat. |
| `func` | Reserved; currently empty. |

The expression runs via `new Function("ctx", "data", "func", "vars",
"\"use strict\"; return (<your expression>);")`. Standard JS is
available (template literals, optional chaining, spread, etc.).

## Shapes you will see in a lowered workflow

### An upstream step reference

```json
"messages": "js/ctx.state.fetch.data.items"
```

`ctx.state[<step-id>]` holds the upstream step's output. Authored as the
handle `fetched.data.items`, or as
`{"$ref": {"step": "fetch", "path": ["data", "items"]}}` in JSON.

### A composed string

```json
"channel": "js/`chat:${ctx.request.params.sessionId}`"
```

Authored as `` tpl`chat:${req.params.sessionId}` ``, or as
`{"$tpl": ["chat:", {"$ref": {"step": "@trigger", "path": ["params", "sessionId"]}}]}`.

### An escape hatch

Expressions with no structural equivalent — fallbacks, optional chaining,
`.map`/`.reduce`, calls, `process.env` reads — are the sanctioned escape hatch
(ADR 0008). They are authored with the `` js`…` `` tagged template in
TypeScript, and stay `js/…` strings in JSON, because there is nothing to lower
them to:

```json
"model": "js/process.env.OPENROUTER_MODEL || 'openai/gpt-4o-mini'"
"value": "js/ctx.state['load-history']?.value || []"
```

These are the one legitimate reason a `js/` string appears in a hand-written
JSON workflow. Everything else should be `{"$ref"}` / `{"$tpl"}` — see the
[legacy expression strings](/c/migration-guides/legacy-expression-strings)
migration guide.

## Positions the lowering pass does not cover

`lowerRefs` is scoped to step `inputs`. These positions are resolved by the
mapper directly and are still written as path strings, in JSON *and* in the
object-style TS API:

| Position | Form |
|---|---|
| `branch.when`, `loop.while` | raw `ctx.*` — **no** `js/` prefix |
| `switch.on`, `switch.cases[].when` | `js/ctx.*` |
| `forEach.in` | `js/ctx.*` |
| `subworkflow` (polymorphic name) | `js/ctx.*` |
| step `idempotencyKey` | `js/ctx.*` |
| trigger `concurrencyKey`, `debounce.key`, `idempotencyKey` | `js/ctx.*` |

The `@blokjs/core` callback DSL takes handles for `forEach`, `switchOn`,
`subworkflow` and step-level `idempotencyKey` and lowers them itself. Trigger
config (`concurrencyKey`, `debounce.key`) is resolved at run-entry, before any
step handle exists, so it stays a path string in every authoring form.

`wait.for` / `wait.until` are the one position OUTSIDE step `inputs` that the
lowering pass does cover: `normalizeWaitStep` lowers a structural `{"$ref"}`
there to the same wire string, and the runner resolves it through this mapper
when the wait step executes (#704). A `js/` string works too, for the
non-structural cases.

## Failure mode (`BLOK_MAPPER_MODE`)

A `js/` expression that throws at run time (typo, undefined access,
syntax error) **fails the step by default** (`strict` mode) — it throws
`MapperResolutionError` with full context. Opt into the old
log-and-pass-through behavior (nice for dev, **dangerous for prod**) with
`BLOK_MAPPER_MODE=warn`. The modes:

| Mode | Behavior on resolution failure |
|---|---|
| `warn` | Log structured warning via `ctx.logger.logLevel("warn", ...)` and pass the literal expression through. The pre-fail-fast v1 behavior; opt-in. |
| `strict` | Throw `MapperResolutionError` with full context (workflow + step + expression + cause + hint). The step fails fast. **Recommended for production.** |
| `silent` | Full suppression (no log, no throw). Pre-v0.3 behavior. Opt-out for tests / workflows that intentionally use undefined-tolerant resolution. |

```bash
# Production
BLOK_MAPPER_MODE=strict bun run dist/index.js
```

### The structured warning includes:

- Workflow + step
- Expression literal that failed
- Underlying JS error message
- Heuristic hint (e.g. *"the path `ctx.req.body` is undefined or
  doesn't have a `userId` field — check the trigger payload"*)
- The fix prompt (*"set `BLOK_MAPPER_MODE=strict` to fail fast"*)

`MapperResolutionError` is exported from `@blokjs/shared` for
`instanceof` checks in custom error handlers.

## Legacy forms still accepted at load

The runner keeps accepting older wire shapes so existing workflows load
unchanged. It logs one deprecation warning per workflow that still carries
hand-written path strings in step inputs, naming the workflow and the offending
steps; silence it in CI with `BLOK_SUPPRESS_LEGACY_EXPR_WARNING=1`. Support for
hand-written path-string inputs is removed in the next major.

| Legacy | Current | Notes |
|---|---|---|
| `ctx.vars['x']` | `ctx.state.x` | `ctx.vars` still resolves as an alias of `ctx.state`. |
| `ctx.response.data` / `ctx.prev.data` | `ctx.state.<producing-step>.data` | The aliases still resolve, but name the producing step — that is what a structural ref lowers to. |
| `${path}` interpolation | a `js/` template literal | The runner still parses `${path}` for back-compat but warns. Author it as `` tpl`…` `` / `{"$tpl": […]}`. |

## Security

The expression runs via `new Function()` — full JS execution. **NEVER
build expression strings from untrusted input.** Workflow definitions
are static, authored artifacts compiled at the load boundary, so this is safe
under v2. If you need to evaluate user-supplied expressions (e.g. an arithmetic
calculator), use a sandboxed math parser like `mathjs` inside a node — not the
mapper. See the [threat model](/d/security/threat-model).
