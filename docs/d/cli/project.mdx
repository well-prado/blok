Managing **Blok** projects effectively starts with the `blokctl` CLI. This section focuses on commands related to project creation and overall project lifecycle management, primarily the `create project` command.

<Tip>
New to Blok? [The quickstart](/d/get-started/quickstart) walks through scaffolding a
project, writing a node, and composing a workflow in about five minutes. This page is
the command reference — what each flag does and what actually lands on disk.
</Tip>

## `create project`

This is typically the first `blokctl` command you will use when starting a new **Blok** application.

> <sub>**Purpose**: To scaffold a new **Blok** project with a predefined directory structure, necessary configuration files, and optional templates.</sub>

**Usage**:

```bash
# This command creates a new project and automatically generates a new directory for it.
npx blokctl@latest create project
```
```bash
# Use this command to create a new project inside the current (empty) directory.
npx blokctl@latest create project .
```

**Interactive Prompts & Options**:

When you run `npx blokctl@latest create project`, the CLI will guide you through a series of prompts:

1. Assign a project name.
2. Select a package manager: **npm** (default), yarn, pnpm, or bun.
3. Select **triggers** to install — **HTTP** (default) plus, optionally, SSE, WebSocket, Pub/Sub, Worker, or Cron.
4. The generated project records the Node.js target by default; add any cross-language sidecars (Python3, Go, Rust, Java, C#, PHP, Ruby, or Swift) when needed. Swift requires Swift 6.1+ and is production-supported on Linux.
5. Pick any **observability modules** to enable (all optional — see [`blokctl observability`](./observability.mdx)).
6. **Install the examples? YES** (recommended for a first project — it adds runnable sample workflows and nodes beyond the one shipped by default).

**Non-interactive flags** (for CI/scripts):

| Flag | Purpose |
| --- | --- |
| `-n, --name <value>` | Project name |
| `-T, --triggers <list>` | Comma-separated triggers (e.g. `http,worker`) |
| `-r, --runtimes <list>` | Comma-separated language sidecars (default `node`) |
| `-m, --package-manager <value>` | `npm` (default), `yarn`, `pnpm`, or `bun` |
| `--pubsub-provider <value>` | Pub/Sub provider when `pubsub` is selected: `gcp` (default), `aws`, `azure` |
| `--queue-provider <value>` | Queue provider when `queue`/`worker` is selected: `kafka` (default), `rabbitmq`, `sqs`, `redis` |
| `--observability <list>` | Comma-separated observability modules to enable (e.g. `tracing,trace-store`) |
| `--obs-stack <tier>` | Local dev stack: `none` (default), `lite`, or `full` |
| `--examples` | Install example workflows and nodes |

<Note>
**The dev stack defaults to `none`.** Earlier versions copied a full Prometheus/Grafana/Loki/Tempo stack into every project; now you opt in with `--obs-stack lite|full` (or add it later via `blokctl observability add obs-stack`).
</Note>

<Note>
`-l, --local <path>` scaffolds from a local Blok repo checkout instead of the published npm
packages. It's a framework-development flag, not something a typical project author needs.
</Note>

**What it Does**:

Upon completion, the `npx blokctl@latest create project` command will:

1. Create a new directory with your desired project name, or use the current directory instead.
2. Install dependencies with the chosen package manager.
3. Populate the directory with the standard **Blok** project structure. This includes:
   - `src/nodes/<name>/index.ts` — your own nodes. Each is **auto-discovered** and registered
     by its `defineNode({ name })` — there's no registry to edit.
   - `src/Nodes.ts` — generated glue, not a registry you maintain: it imports published (npm)
     node packages and merges them with the nodes auto-discovered from `src/nodes/`.
   - `src/workflows/**/*.ts` — TypeScript workflows written with the typed-handle DSL
     (`workflow()` / `step()`). **Auto-routed from the filesystem** — a file's path derives its
     URL (`src/workflows/users/[id].ts` → `/users/:id`), the same way JSON workflows already
     work. No registration step for a new workflow in this directory.
   - `src/Workflows.ts` — an **optional, back-compat** registration map, not something new
     workflows need. Useful for a workflow that lives outside `src/workflows/` or during a
     gradual migration; a workflow present in both the scan and the map still resolves to one
     route.
   - `workflows/json/` — JSON-format workflows (interop / migration), auto-routed the same way
     as the TypeScript ones.
   - `src/triggers/<trigger>/` — the generated trigger runtime (e.g. the HTTP server). Framework
     code you don't normally hand-edit; `src/triggers/http/AppRoutes.ts` is the one file there
     meant for your own plain Hono routes.
   - `package.json` with `dev` (`blokctl dev`), `build` (`tsc`), and `start` (`node dist/...`)
     scripts, and `tsconfig.json` targeting **NodeNext** module resolution, so the built output
     runs under plain Node with no extra loader.
   - `.env.example` and `.env.local` for environment variables (`PORT`, `WORKFLOWS_PATH`,
     `NODES_PATH`, …).
   - `AGENTS.md` and `CLAUDE.md` — not a `README.md` — authoring guides written for an AI
     coding agent working in the new project.
   - `.blok/` (gitignored) — the local SQLite trace database `blokctl dev` and Blok Studio use.
   - `Dockerfile` / `Dockerfile.dev` for production and dev container builds.
   - `.gitignore` and a lockfile matching the chosen package manager.
4. If examples are selected, it installs additional sample node and workflow implementations on top of the one runnable example the default scaffold already ships.

<Accordion title="Advanced: registering a workflow by hand (src/Workflows.ts)">
`src/Workflows.ts` is a back-compat / advanced path. Use it when a workflow lives outside
`src/workflows/` (a shared package, a different directory), or during a migration where you
want an explicit map alongside the scan.

```ts src/Workflows.ts {2,6}
// ...existing imports
import myWorkflow from "./workflows/my-workflow";

const workflows = {
  // ...existing entries
  "my-workflow": myWorkflow,
};

export default workflows;
```
</Accordion>

**Initialize**:

Navigate to your project and start the dev server — hot reload plus Blok Studio, the live trace viewer:

```sh
cd your-project-name
npm run dev
```
Your server will be running at:
`http://localhost:4000/health-check`, with Blok Studio at `http://localhost:4000/__blok`.

For a production-shaped run under plain Node — no `blokctl` wrapper — build first:

```sh
npm run build
npm run start
```
