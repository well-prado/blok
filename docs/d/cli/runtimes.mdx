Blok runs workflow steps across JavaScript targets (**Node.js, Bun, and Deno**)
plus the supported language runtimes, including **Elixir, Swift, and Dart**, and the distinct `runtime.wasi`
Component Model boundary. JavaScript target selection is a project setting; it
is separate from the package manager and from the language sidecars managed by
the commands below. The WASI boundary is contract-first in the current
release; its long-lived Rust/Wasmtime host is not bundled yet.

You choose which runtimes you want when you scaffold a project (`create project --runtimes go,python3`). But you don't have to decide everything up front: the **`blokctl runtime`** commands let you **add or remove a language at any time**, in place, on a project that already exists.

<Note>
Existing projects without an explicit setting continue to target Node.js. The
canonical project values are `node`, `bun`, and `deno`; the canonical workflow
step kinds are `runtime.nodejs`, `runtime.bun`, and `runtime.deno`. The runtime
target does not select npm, pnpm, Yarn, or Bun as a package manager.
</Note>

<Note>
All three targets execute. When the engine hosting the orchestrator IS the
selected target, steps run in-process with zero overhead; otherwise they run in
a persistent `@blokjs/runtime-worker` process for that engine, reached over the
same gRPC contract the language sidecars use. Blok never substitutes a
different JavaScript engine — a missing or unreachable worker fails the step
with the exact command to start it. See
[ADR 0016](../../architecture/adr-0016-javascript-runtimes.md).
</Note>

## Choosing a JavaScript target

| | Node.js (`node`) | Bun (`bun`) | Deno (`deno`) |
| --- | --- | --- | --- |
| Step kind | `runtime.nodejs` | `runtime.bun` | `runtime.deno` |
| Worker gRPC port | `10012` | `10013` | `10014` |
| TypeScript | via your build (`tsc`) | native | native |
| npm packages | native | native | via node compatibility |
| Permission boundary | none (Blok capability policy only) | none (Blok capability policy only) | native `--allow-*`, derived from declared capabilities |
| Minimum version | 20 | 1.1 | **2.7.5** |
| Pick it when | broadest ecosystem + production compatibility | fastest start-up and an integrated toolchain | you want least-privilege execution enforced by the engine |

<Note>
Deno's Node-compat HTTP/2 **server** could not complete a gRPC connection before 2.7.5: the worker binds its port and then never answers a call, so an older Deno looks like a worker that is not running rather than one that is too old. Bisected against the worker's own integration suite (2.7.4 fails, 2.7.5 passes), and CI pins exactly v2.7.5 so the floor is what CI proves.
</Note>

The target is **independent of the package manager**: `blokctl runtime use bun`
does not switch you to `bun install`, and `--package-manager npm` does not force
Node.js execution.

### The persistent worker

`runtime.nodejs`, `runtime.bun`, and `runtime.deno` steps never spawn a process
per invocation. One long-lived worker per engine serves every step, with health
checks, bounded concurrency, backpressure, cancellation, deadlines, and a
graceful drain on `SIGTERM`. `blokctl dev` starts it for you whenever the
project's target differs from the engine hosting the triggers.

Run one by hand (for a container image, or to point several projects at one
worker):

```bash
# Node.js
GRPC_PORT=10012 node node_modules/@blokjs/runtime-worker/dist/bin.js

# Bun
GRPC_PORT=10013 bun node_modules/@blokjs/runtime-worker/dist/bin.js

# Deno — least privilege: one port, read the project, read env
GRPC_PORT=10014 deno run \
  --allow-net=127.0.0.1:10014 --allow-read=. --allow-env \
  --node-modules-dir=manual node_modules/@blokjs/runtime-worker/dist/bin.js
```

The runner finds it at `RUNTIME_NODEJS_GRPC_PORT` / `RUNTIME_BUN_GRPC_PORT` /
`RUNTIME_DENO_GRPC_PORT` (written into `.env.local` at scaffold time), on
`RUNTIME_<KIND>_HOST` (default `localhost`).

| Environment variable | Default | What it does |
| --- | --- | --- |
| `GRPC_PORT` | per-engine (10012/10013/10014) | Port the worker binds |
| `BLOK_WORKER_NODES` | auto-detected | Project node module (`dist/Nodes.js` under Node.js, `src/Nodes.ts` under Bun/Deno) |
| `BLOK_WORKER_MAX_CONCURRENCY` | `64` | In-flight executions before queueing |
| `BLOK_WORKER_MAX_QUEUE` | `256` | Queued executions before a `WORKER_OVERLOADED` error |
| `BLOK_GRPC_MAX_MESSAGE_BYTES` | 16 MiB | Message ceiling — must match the runner's |
| `BLOK_BLOB_DIR` | unset | Shared claim-check directory; enables `blob-v1` |
| `BLOK_SKIP_JS_WORKER` | unset | `1` stops `blokctl dev` spawning a worker |
| `BLOK_DENO_ALLOW_ALL` | unset | `1` launches the Deno worker with `--allow-all` (diagnosed; never a production default) |
| `BLOK_DENO_ALLOW_NET` | unset | `host[:port],…` scopes the `network` effect's `--allow-net` instead of leaving it unrestricted |
| `BLOK_WORKER_CONFORMANCE` | unset | `1` also serves the portable conformance fixture set, for verifying an engine by hand |

`--print-manifest` prints the worker's runtime capability manifest (engine,
version, protocol version, module formats, TypeScript mode, npm compatibility,
permissions, cancellation, streaming, message ceiling); the same JSON rides on
every `ListNodes` response in the `blok-runtime-manifest` gRPC metadata header.

### Deno permissions

Deno's worker is launched with the least privilege its nodes justify. The
baseline is one bound port, read access to the project (and the claim-check
directory when one is configured), and environment access. Anything more is
**earned by a declared capability** in a node's `capabilityManifest`:

| Declared effect | Additional permission |
| --- | --- |
| `network` | `--allow-net`, scoped by `BLOK_DENO_ALLOW_NET` when set, otherwise unrestricted |
| `filesystem` / `write` | `--allow-write=<project>` |
| `process` | `--allow-run` |

Nothing maps to `--allow-ffi`, so a Deno worker cannot reach native code at
all unless an operator opts out of the boundary entirely. `blokctl dev` prints
each grant with the reason it exists — least privilege you can inspect rather
than take on trust. `--allow-env` is unrestricted by design;
[the troubleshooting page](./runtime-troubleshooting) records the measurement
behind that.

`blokctl dev` reads those declarations from the worker itself before launching
it, so the flags follow the code. `BLOK_DENO_ALLOW_ALL=1` is the only route to
`--allow-all`, and it prints a warning every time.

## What a generated project gets

Selecting a target shapes the scripts `blokctl create project` writes:

| Script | `--runtime node` | `--runtime bun` | `--runtime deno` |
| --- | --- | --- | --- |
| `dev` | `blokctl dev` | `blokctl dev` | `blokctl dev` |
| `typecheck` | `tsc --noEmit` | `tsc --noEmit` | `tsc --noEmit` |
| `build` | `tsc` | `tsc` | `tsc` |
| `test` | `tsc && node --test tests/*.test.js` | `tsc && bun test tests/` | `tsc && deno test … tests/` |
| `start` | `node dist/…` | `bun dist/…` | `node dist/…` |
| `worker:start` | `node …/runtime-worker/dist/bin.js` | `bun …/bin.js` | `deno run --allow-… …/bin.js` |

Two of those deserve a word.

**`typecheck` and `build` are the same for every target.** TypeScript is the
project's type checker and emitter whichever engine runs the output; which
engine executes your nodes is not a type-checking concern, the same way it is
not a package-manager concern.

**`start` is Node.js for a Deno project.** That is the host/target separation
doing its job: `start` boots the *orchestrator*, the Blok runner is not hosted
under Deno, and the project's `runtime.deno` steps run in the worker that
`worker:start` (and `blokctl dev`) launches. Node.js and Bun host the
orchestrator themselves, so selecting them makes `start` use that engine and
their steps run in-process with no worker at all.

The project also ships one test (`tests/nodes.test.js`) written with
`node:test` in plain JavaScript — the one spelling all three engines run
unchanged. It loads the **built** node registry, which is exactly the load the
worker performs, so a node that only resolves under one engine fails there
first. Add your own with `runNode` / `runWorkflow` from `@blokjs/core/testing`.

### Deployment metadata

The worker is a supervised program like every language sidecar, pinned to the
engine version CI proves it against:

```ini
[program:javascript_worker]
; ADR 0016 — persistent deno worker for runtime.deno steps.
; Pinned engine: deno 2.7.5 (the version CI proves this worker against).
command=deno run --allow-net=127.0.0.1:10014,localhost:10014 --allow-read=. --allow-env --node-modules-dir=manual node_modules/@blokjs/runtime-worker/dist/bin.js
directory=/app
environment=GRPC_PORT="10014",HOST="0.0.0.0"
autostart=true
autorestart=true
```

The generated `Dockerfile` builds on a Bun image, so a `node` or `deno` target
also gets a pinned engine layer in the release stage:

```dockerfile
# Blok JavaScript execution target: deno (ADR 0016).
COPY --from=denoland/deno:bin-2.7.5 /deno /usr/local/bin/deno
```

<Note>
In development, `blokctl dev` supervises every sidecar — including this worker
— with bounded restart and backoff. A crash is restarted; a crash **loop** is
capped and reported once rather than flooding the log.
</Note>

## The commands at a glance

| Command | What it does |
| --- | --- |
| `blokctl runtime use <node\|bun\|deno>` | Change the project's JavaScript execution target |
| `blokctl runtime add <lang>` | Install a language sidecar into this project |
| `blokctl runtime remove <lang>` | Remove a language sidecar from this project |
| `blokctl runtime list` | Show what's installed and what you can add |

Run them from your project's root (or point at it with `-d <path>`). `remove` has the alias `rm`, and `list` has `ls`.

### `runtime use` — select the JavaScript target

The selection is written to `.blok/config.json` without changing the package
manager, trigger configuration, or language sidecars:

```bash
blokctl runtime use node
blokctl runtime use bun
blokctl runtime use deno
```

Legacy `nodejs`, `typescript`, and `ts` inputs are accepted once and normalized
to the canonical project value `node` with a deprecation warning. The command
changes only the declared target: the worker for the new engine is started by
the next `blokctl dev`, and a project never silently runs a Bun or Deno
selection under Node.js.

<Tip>
Not sure where to start? Run `blokctl runtime list` to see what's installed and which languages your machine already has the toolchain for — then `blokctl runtime add` (with no argument) to pick one from an interactive menu.
</Tip>

A read‑only snapshot: which sidecars are installed (with their gRPC port and detected version), and which supported languages are still available to add (with whether the toolchain is ready on your machine).

```bash
blokctl runtime list
```

│

│  ✓ Python 3     gRPC :10007    python3 3.9.6  │

Add `--json` for a machine‑readable version (handy in scripts or CI):

```bash

```

The JSON output reports the selected JavaScript target separately from language
sidecars, and reports it **truthfully**: it probes the engine's binary and
version rather than assuming the config is achievable.

```json

    "kind": "runtime.deno",
    "execution": "persistent-worker",
    "available": false,
    "binary": "deno",
    "version": null,

    "grpcPort": 10014,

  }
}
```

commands yet.

## `runtime add` — add a language

This is the command you'll reach for when you scaffolded a project with, say, just Node and later realize you want to write a step in Python or Go.

```bash
# Add a specific runtime
blokctl runtime add python3

# …or omit the name to pick one from an interactive menu
blokctl runtime add
```

<Steps>
  <Step title="Checks the toolchain">
    Confirms the language is installed (e.g. `python3`, or `java` **and** `mvn`). If it isn't, you get the install link — or pass `--skip-toolchain-check` to scaffold anyway.
  </Step>
  <Step title="Fetches a version‑matched SDK">
    Downloads the SDK source for **your project's Blok version**, so the gRPC contract always matches your `@blokjs/runner`. (Cached under `~/.blok`, so the next add is instant. Use `--local <path>` to point at a checkout instead.)
  </Step>
  <Step title="Builds it">
    Runs the language's install/build (`pip install`, `go mod download`, `cargo build`, …). Nothing is written to your project until this succeeds, so a failed build never leaves you half‑configured.
  </Step>
  <Step title="Wires it in">
    Merges the runtime into `.blok/config.json`, `.env.local`, and `supervisord.conf`, and creates `runtimes/<lang>/nodes/` for your code. Your triggers and any other runtimes are left untouched.
  </Step>
</Steps>

After a successful add you'll see exactly what changed:

```text
◇  Python 3 added ─────────────────────────────────────────╮
│  ✓ .blok/config.json   runtimes.python3                  │
│  ✓ .env.local          RUNTIME_PYTHON3_GRPC_PORT=10007    │
│  ✓ supervisord.conf    [program:python3_runtime]         │
│  ✓ runtimes/python3/nodes/  (your runtime nodes go here)  │
├────────────────────────────────────────────────────────────╯
│
└  Run blokctl dev to start it, then add type: "runtime.python3" steps to your workflows.
```

<Note>
**No application code changes are needed.** The runner already knows how to dispatch to all eight sidecar languages — adding one is purely configuration plus the SDK files. You never touch `@blokjs/runner` or your trigger code.
</Note>

### Use it in a workflow

A step runs on a sidecar when you reference a node by name and tag it with its
runtime. Write your node under `runtimes/<lang>/nodes/`, then declare the step:

```json JSON workflow
{
  "id": "resize",
  "use": "image-resizer",
  "type": "runtime.python3",
  "inputs": { "image": { "$ref": { "step": "@trigger", "path": ["body", "image"] } } }
}
```

<Note>
**`runtimeNode` is the typed TS form for a cross-runtime step.** `@blokjs/core`
exports `runtimeNode<In, Out>(name, "runtime.<lang>")` as a real value (issue
#424) — it gives you typed inputs/outputs for a cross-runtime node, and `step()`
lowers it to the same `{ use, type: "runtime.<lang>" }` step the JSON form above
produces, so the runner routes it through the gRPC runtime adapter. The
`blokctl nodes sync` stubs are these `runtimeNode(...)` values; import and use
them directly:

```ts
import { workflow, step, runtimeNode, http } from "@blokjs/core";

// typed cross-runtime stub — executes via the runtime adapter
const resizeImage = runtimeNode<{ image: string }, { url: string }>(
  "image-resizer",
  "runtime.python3",
);

export default workflow("Resize Image", { version: "1.0.0", trigger: http.post("/resize") }, (req) => {
  step("resize", resizeImage, { image: req.body.image });
});
```

The second argument is the runtime kind (`"runtime.python3"`); the
`blokctl nodes sync` stubs pass the catalog ref (`"runtime.python3:image-resizer"`)
in the same slot — `step()` accepts either and derives the kind from it.
</Note>

Then start everything together:

```bash
blokctl dev
```

`blokctl dev` reads `.blok/config.json`, spawns each sidecar, waits for its gRPC port to come up, and then starts your triggers — exactly as if you'd scaffolded the runtime at project creation.

### Options

| Flag | Purpose |
| --- | --- |
| `-d, --directory <path>` | Project directory (default: current directory) |
| `--local <path>` | Use a local Blok checkout for the SDK source instead of fetching by version |
| `--grpc-port <port>` | Use a non‑default gRPC port for this runtime |
| `--force` | Reinstall even if the runtime is already present (does a clean re‑copy) |
| `--skip-toolchain-check` | Add even if the language toolchain isn't detected |
| `-y, --yes` | Skip prompts (non‑interactive — for CI/scripts) |

<Warning>
**Toolchain not installed?** `add` stops with the exact tool you're missing and a link to install it — for example, *"Java toolchain not detected (need **Maven**). Install Maven: …"*. Install it and re‑run, or pass `--skip-toolchain-check` if you'll set it up later.
</Warning>

## `runtime remove` — remove a language

Cleanly undoes everything `add` did — and it's careful with your code.

```bash
blokctl runtime remove go
```

<Steps>
  <Step title="Warns you about dependent workflows">
    First it scans your project for steps that use `runtime.<lang>` and lists the files. Those steps will fail once the sidecar is gone, so you know exactly what to update.
  </Step>
  <Step title="Asks before deleting your nodes">
    Your runtime nodes in `runtimes/<lang>/nodes/` are **kept by default**. `remove` asks before deleting them; pass `--purge-nodes` to delete them without a prompt.
  </Step>
  <Step title="Undoes the wiring">
    Removes the entry from `.blok/config.json`, the `RUNTIME_<LANG>_*` vars from `.env.local`, the `supervisord.conf` block, and the `.blok/runtimes/<lang>/` SDK directory.
  </Step>
</Steps>

```text
▲  1 workflow file(s) reference runtime.python3 — those steps will fail after removal:
   • src/workflows/demo.ts
◇  Python 3 removed ───────────────────────────────────────╮
│  − .blok/config.json   runtimes.python3                  │
│  − .env.local          RUNTIME_PYTHON3_*                  │
│  − supervisord.conf    [program:python3_runtime]         │
│  − .blok/runtimes/python3/  (SDK source + build output)  │
├────────────────────────────────────────────────────────────╯
│
└  Update the 1 workflow(s) that referenced runtime.python3. Re-add anytime: blokctl runtime add python3.
```

<Warning>
Any workflow step with `type: "runtime.<lang>"` will fail at run time after you remove that language. Update or delete those steps — or just `blokctl runtime add <lang>` to put it back. Removal is fully reversible.
</Warning>

### Options

| Flag | Purpose |
| --- | --- |
| `-d, --directory <path>` | Project directory (default: current directory) |
| `--purge-nodes` | Also delete your custom nodes in `runtimes/<lang>/nodes/` |
| `-y, --yes` | Skip prompts (keeps your custom nodes) |

## How runtimes are wired (under the hood)

If you're curious what these commands actually change, a runtime lives in **four places** — and that's the whole story. There's no hidden state, and nothing in your application code:

| Where | What's there |
| --- | --- |
| `.blok/config.json` → `runtimes.<lang>` | The runtime's command, ports, version, and working directory |
| `.env.local` → `RUNTIME_<LANG>_*` | Host + gRPC port the runner connects to |
| `supervisord.conf` → `[program:<lang>_runtime]` | How the sidecar boots in a container deploy |
| `.blok/runtimes/<lang>/` + `runtimes/<lang>/nodes/` | The SDK server (managed) + **your** runtime nodes (yours) |

Each language has a fixed default gRPC port:

| Runtime | gRPC port |
| --- | --- |
| Go | `10001` |
| Rust | `10002` |
| Java | `10003` |
| Kotlin | `10011` |
| C# / .NET | `10004` |
| PHP | `10005` |
| Ruby | `10006` |
| Python 3 | `10007` |
| Swift | `10008` |

Because it's all configuration, a runtime added later is **indistinguishable** from one you picked at `create project` — same files, same shape, started the same way by `blokctl dev`.

## FAQ

<AccordionGroup>
  <Accordion title="I scaffolded my project with only Node. How do I add Go?">
    `cd` into the project and run `blokctl runtime add go` (you'll need the Go toolchain installed). That's it — write your Go nodes in `runtimes/go/nodes/`, reference them with `type: "runtime.go"` steps, and `blokctl dev` will start the Go sidecar alongside your triggers.
  </Accordion>
  <Accordion title="Will removing a runtime delete my code?">
    No — not unless you ask. Your nodes in `runtimes/<lang>/nodes/` are kept by default; `remove` prompts before touching them and only deletes them if you confirm (or pass `--purge-nodes`). It does delete the managed SDK directory under `.blok/runtimes/<lang>/`, which is regenerated by `add`.
  </Accordion>
  <Accordion title="The gRPC port is already in use.">
    `add` refuses if the runtime's default port is taken (by another runtime in the project, or a live process on your machine) and tells you to pass `--grpc-port <n>`. The override is threaded everywhere consistently — config, `.env.local`, and the boot command.
  </Accordion>
  <Accordion title="Does this match `create project --runtimes`?">
    Yes, exactly. `runtime add` reuses the same setup code and writes the same configuration, so a runtime added later behaves identically to one scaffolded at creation. `blokctl dev` and the runner can't tell the difference.
  </Accordion>
  <Accordion title="What if my project is on an unreleased / local Blok version?">
    `add` fetches the SDK that matches your project's pinned `@blokjs/runner` version, so the gRPC contract always lines up. If that version isn't published (e.g. you're developing Blok itself), point at a local checkout with `--local /path/to/blok`.
  </Accordion>
</AccordionGroup>
